# SAST Link v2 OAuth/OIDC 接入

> 本服务为标准 **OAuth 2.1 + OpenID Connect Provider**，不提供 SDK。端点能力以 discovery 为准。

## 1. 基础信息

| 项 | 值 |
| --- | --- |
| Discovery | `GET https://link.sast.fun/v2/.well-known/openid-configuration` |
| Issuer | `https://link.sast.fun/v2`（各端点 URL 由 `JWT_ISSUER` 派生，与 ID Token `iss` 同源） |
| 授权流程 | 仅授权码流（`response_type=code`）；grant type：`authorization_code` / `refresh_token` |
| PKCE | 强制 S256；`code_challenge` 固定 43 字符 base64url，其他长度返回 `invalid_request` |
| 客户端认证 | `client_secret_post` 或纯 PKCE；**不支持 `client_secret_basic`** |
| 签名 | Access Token / ID Token 均为 EdDSA（Ed25519）JWT；JWKS：`/.well-known/jwks.json`（`kid: link-v2-active`） |
| `request` / `request_uri` / `claims` 参数 | 不支持 |
| `max_age` / `prompt` | 未实现 |
| 纯 OAuth2（无 `openid`） | **不支持**：所有 scope 请求必须含 `openid`，否则 `invalid_scope` |

## 2. 客户端模型

- 客户端一律经控制台注册（`POST /admin/oauth-clients`，API 文档 §6.7）。
- `first_party`：公开客户端，无 `client_secret`，token 端点仅凭 PKCE 认证；携带 secret 返回 `invalid_client`。
- `third_party`：机密客户端，token 端点必须 `client_secret_post`。
- `redirect_uris` **精确字符串匹配**，前缀/通配不成立；授权请求与兑换请求的 `redirect_uri` 都必须与注册值完全一致。
- 客户端认证失败共用同一条 `error_description`（不区分客户端不存在 / 类型搞错 / secret 错），防枚举。
- scope 收窄或新授能力 scope 时，该客户端全部存量 token 在同一事务内撤销；consent 与授权码兑换两处还会对照活注册重查 scope。

## 3. 授权端点

```
GET /oauth/authorize
```

| 参数 | 约束 |
| --- | --- |
| `response_type` | 固定 `code` |
| `scope` | 必须含 `openid`；必须是该客户端注册 scope 的子集 |
| `state` | 必填，最长 512 |
| `code_challenge` | 必填，43 字符 base64url |
| `code_challenge_method` | 必填，仅 `S256` |
| `nonce` | 可选，最长 255 |

- 两段式 consent（本端点不要求认证 → 302 至 SAST Link 前端授权页 → 用户同意后回 `redirect_uri`），对 RP 透明。
- 按 IP 限流（默认 300 次/60s，`RATE_LIMIT_AUTHORIZE_RPM`）。
- 错误重定向：`client_id` / `redirect_uri` 校验通过**前**的错误（`invalid_request`、`invalid_client`、`temporarily_unavailable`、`server_error`）去 SAST Link 前端错误页，**不带 `state`**——RP 收不到任何回调；校验通过**后**的错误（`unsupported_response_type`、`invalid_scope`、`unauthorized_client`、`invalid_request`）重定向至 `redirect_uri`，带 `error` / `error_description` / `state`。`invalid_request` 出现在两侧：通过前指 `client_id` / `redirect_uri` 本身不合法，通过后指其余参数不合法。

## 4. Token 端点

```
POST /oauth/token   （application/x-www-form-urlencoded）
```

- 参数只从请求体读取，query string 被忽略；重复参数直接拒绝。
- 错误格式：RFC 6749 §5.2。`invalid_client` 为 HTTP 401（**不带 `WWW-Authenticate`**：本服务不经 HTTP Basic 认证，discovery 的 `token_endpoint_auth_methods_supported` 仅 `none` / `client_secret_post`），其余 400；限流 `temporarily_unavailable` 429 带 `Retry-After`（默认 300 次/60s，与 `/oauth/revoke` 共用）。
- 成功响应带 `Cache-Control: no-store` 与 `Pragma: no-cache`。

### 4.1 授权码兑换

- 授权码 TTL 5 分钟（`OAUTH_CODE_TTL`），单次使用。
- **PKCE 校验失败同样消耗授权码**（防 verifier 枚举），失败必须重走授权。
- 授权码重放触发 family 级联撤销（首兑签发的 access/refresh token 一并作废）。
- 签发时快照 `token_version` 并在事务内重验，与「cut access now」类撤销（改密、降权、关户、客户端停用/收窄）串行化。

### 4.2 Refresh

- 轮换式：旧 refresh token 立即撤销；重放撤销**整条 family**（`refresh_replayed` 审计）。
- 轮换后 30s 宽限窗内的并发刷新视为良性，不撤销 family。
- **不支持 scope 收窄**：轮换后 scope 与原授权完全一致（RFC 6749 §6 允许的收窄在此不成立），如需更小 scope 须重新走一次授权流程。
- 携带 `user:*` / `admin:*` 的 family 受 `JWT_REFRESH_CAPABILITY_MAX_LIFETIME`（默认 168h，0 关闭）封顶：从 family 首次授权起算，每次轮换都按 `origin+cap` 夹紧，到点撤销（`invalid_grant`，审计 `refresh_family_expired`），须重新授权。纯 OIDC family 不封顶。
- 刷新不更新 `auth_time`。

### 4.3 有效期

| Token | 默认有效期 | 说明 |
| --- | --- | --- |
| Authorization Code | 5m | 单次使用 |
| Access Token | 1h | `expires_in: 3600` |
| Refresh Token | 720h | 轮换式；能力 family 另受 168h 封顶 |

## 5. 撤销端点

`POST /oauth/revoke`，RFC 7009。与 `/oauth/token` 共用限流器。未知或已撤销的 token 一律返回 `200`（RFC 7009 §2.2），本端点不暴露 token 是否存在。

## 6. Token 形态与 claim

### 6.1 Access Token

EdDSA JWT。业务相关 claims：`kid`、`jti`、`sub`、`role`、`state`、`token_version`、`scope`、`azp`（标准 JWT 的 `iss` / `aud` / `exp` / `iat` / `nbf` 等未列）。用于 `/userinfo` 及以本服务为 resource server 的受保护资源。`role` 是签发时快照；本服务自身鉴权读数据库行而非 token 的 `role`。

### 6.2 ID Token

`openid` scope 触发签发。Claims：

| Claim | Scope 要求 | 说明 |
| --- | --- | --- |
| `iss` / `sub` / `aud` / `exp` / `iat` | — | 标准。`sub` 为用户 ID 字符串（**稳定标识，用它做账号关联**），`aud` 为 `client_id` |
| `nonce` | 授权请求携带时 | 原样返回 |
| `auth_time` | — | 见下方偏差说明 |
| `name` / `picture` / `preferred_username` / `updated_at` | `profile` | `preferred_username` 取昵称，空白回退真名 |
| `role` | `profile` | 本服务自有 claim，取值见 API 文档附录 A。取自**签发时的数据库行**，随 token 过期；**仅作展示提示，不可作为授权判断依据** |
| `email` / `email_verified` | `email` | `email` 为登录邮箱（`login_email`）；`email_verified` 恒 `true` |

**`auth_time` 偏差（已知限制）**：值为授权码创建时刻（即用户在授权页点击同意的时点）；轮换后保持该 family 首个 refresh token 的创建时刻，不随刷新更新——服务端未持久化真实认证时刻。该 claim 会签发但**不在 `claims_supported` 中通告**，RP 不应将其当作认证新鲜度依据。

### 6.3 UserInfo

`GET` / `POST /userinfo`，Bearer 认证（`AuthenticateAnyClient`：任何客户端签发的有效 token 均可，无 `azp` 门）。返回裸 claim 集合，无业务信封；claim 过滤与 ID Token 同门，未授权 scope 的 claim **不出现**（非空值）。能力 scope（`admin:*` / `user:*`）不贡献任何 claim。错误为 RFC 6750 格式：401 + `WWW-Authenticate: Bearer realm="sast-link", error="invalid_token"` 挑战头（header 中**无** `error_description`：挑战头参数限 US-ASCII 字符集，中文描述放不进，只进 body）。

## 7. Scope 状况

| Scope | 客户端约束 | 作用 |
| --- | --- | --- |
| `openid` | 无 | 必选；触发 ID Token，UserInfo 至少返回 `sub` |
| `profile` | 无 | OIDC claim：`name`/`picture`/`preferred_username`/`role`/`updated_at` |
| `email` | 无 | OIDC claim：`email`/`email_verified` |
| `user:read` | 无 | 访问 `/user/*` 读端点（仅 token 主体本人记录） |
| `user:write` | 无 | 访问 `/user/*` 读+写端点 |
| `admin:read` | 仅 `third_party` | 访问 `/admin/*` 读端点（主体须 admin 角色） |
| `admin:write` | 仅 `third_party` | 访问 `/admin/*` 写端点（主体须 admin 角色） |

- 能力 scope 不产生 OIDC claim：`openid admin:read` 与 `openid` 拿到的字段完全一致。
- 角色门与 scope 门互不蕴含且都必过：`/admin/*` 要求 token 带 admin scope **且**主体为 admin 角色（角色每次请求读数据库行，降权下一请求生效）。
- 内置控制台 token 豁免 scope 门。

## 8. 错误处理状况

按端点分三组：

| 端点 | 格式 |
| --- | --- |
| `/oauth/authorize`、`/oauth/token`、`/oauth/revoke` | RFC 6749：`{error, error_description}` |
| `/userinfo` | RFC 6750：401 + `WWW-Authenticate: Bearer error="invalid_token"` + `{error, error_description}` body |
| `/user/*`、`/admin/*`、其余内部 API | 业务信封 `{code, message, data}`，业务码见 API 文档 §2 |

内部 API 业务码要点：`40300`（角色不足 / 缺能力 scope / 第三方 token 打内部端点，统一此码）、`42900`（限流，带 `Retry-After`）、`50300`（**唯一不满足 `{HTTP状态}{序号}` 规则的码**：对应两个 HTTP 状态——502 为 GitHub / 飞书等第三方 provider 故障，503 为本服务自身依赖（Redis / COS 审核）不可用；两种情况都带 `50300`，均按「稍后重试」处理）。

## 9. 对标准的偏差与已知限制

| # | 项 | 状况 |
| --- | --- | --- |
| 1 | `auth_time` | 值为授权确认时刻而非认证时刻；签发但不通告；`max_age`/`prompt` 未实现 |
| 2 | 纯 OAuth2 | 不支持，`openid` 必选 |
| 3 | refresh scope 收窄 | 不支持（RFC 6749 §6 允许，本服务轮换后 scope 原样继承） |
| 4 | `client_secret_basic` | 不支持，仅 `client_secret_post` / 纯 PKCE；`invalid_client` 401 不带 `WWW-Authenticate` |
| 5 | `code_challenge` | 固定 43 字符 base64url（即 S256 输出长度），其他长度 `invalid_request` |
| 6 | 客户端认证错误 | 全场景统一 `error_description`（防枚举） |
| 7 | token 端点参数 | 忽略 query string；重复参数拒绝 |
| 8 | 能力 scope refresh | 168h 生命周期封顶（`JWT_REFRESH_CAPABILITY_MAX_LIFETIME`） |
| 9 | refresh 重放 | 撤销整条 family（30s 宽限窗除外） |
| 10 | `role` claim | OIDC 标准之外的自有 claim，仅作展示提示 |
| 11 | `state` | 必填（与 OAuth 2.1 一致）；authorize 校验前错误不重定向至 RP 回调 |
